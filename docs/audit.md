# Аудит проекта Setanta Sports Platform

## Коротко

Проект в приличной инженерной форме для той стадии, на которой находится: слой транспорта и запросов (`src/api` → `src/features` → экраны) выстроен аккуратно, единственная точка `fetch`, корректный single-flight refresh, строгий TS без `any` и без `@ts-ignore`. Критичных дефектов внутри приложения нет; самые дорогие — незакрытая цепочка `requestAnimationFrame` в поповере денег, неатомарное сохранение бренда с договорами и выдуманный график «Динамика за 14 дней» на экране, который работает с API и виден рекламодателю. Основная масса проблем лежит вокруг кода, а не в нём: нет ни одного автоматического барьера перед деплоем, документация отстала на 44 коммита и активно врёт, seed-скрипты заводят на публично доступном стенде учётки с угадываемыми паролями. Незавершённая миграция с мока на API даёт второй пласт: четыре раздела по-прежнему живут в `localStorage`, и один из них — «Отчёт» — открыт внешнему клиенту. Первая неделя работы почти целиком состоит из правок на час каждая; переписывать ничего не нужно.

## Что сделано хорошо

- Единственная точка сети на весь проект — `src/api/client.ts:79`. Ни одного прямого `fetch`/axios/XHR в компонентах, WebSocket и EventSource нет.
- Обновление токена сделано через общий промис с проверкой, не сменился ли access, пока запрос был в пути (`src/api/client.ts:103-131`). Типовая гонка при нескольких параллельных 401 здесь закрыта, refresh одноразовый с ротацией.
- Файлы скачиваются транспортом с токеном, а не прямой ссылкой (`src/features/files/queries.ts:51-64`) — прямая ссылка дала бы 401.
- Доменные типы собраны в одном месте (`src/api/types.ts`, 282 строки), `strict: true`, ноль `any`, `@ts-ignore` и `@ts-expect-error`, четыре каста на весь проект.
- Состояния UI закрыты во всех живых API-разделах: Loader на `isPending`, EmptyState с текстом ошибки и кнопкой «Повторить» на `isError`, отдельный EmptyState на пустой список (`src/pages/Advertisers.jsx:139`, `src/pages/Users.jsx:101`, `src/pages/ContractOverview.jsx:442`, `src/pages/Campaigns.jsx:814`).
- Все удаления идут через общий `useConfirm` — восемь мест, единый диалог, единый текст.
- React-код чистый: производные данные считаются на рендере вместо дублирования в состоянии, мутаций состояния нет, условных вызовов хуков нет.
- Комментарии объясняют решения, а не пересказывают код, и честно фиксируют компромиссы: `src/api/endpoints/contracts.ts:9-13`, `src/features/advertisers/queries.ts:20-23`, `src/features/campaigns/queries.ts:13-18`, `vite.config.js:5-6`.
- Ноль `dangerouslySetInnerHTML` и ноль `console.*` в `src/`.

## Высокий приоритет

### 1. Пароли демо-учёток на стенде выводятся из названия бренда; admin/admin опубликован в README

**Где:** `scripts/seed-stand.mjs:40, 238-279, 396`, `README.md:22-23`

**Проблема.** Скрипт переноса сида генерирует логин, почту и пароль детерминированно из названия бренда: `passwordFor = (name) => slugOf(name) + '12345'`. Названия брендов лежат в том же репозитории (`src/lib/seed.js:11-107`: Artel, Click, Korzinka, Payme, Coca Cola и т. д.), то есть пароли вида `artel12345`, `cocacola12345` угадываются с первого раза. Дефолт `--login admin --password admin` повторён в четырёх seed-скриптах, а README прямо публикует рабочую пару admin/admin для стенда.

**Чем грозит.** Стенд `https://setanta.pythonanywhere.com` доступен из интернета. Любой, кто видел репозиторий или просто перебрал названия брендов Setanta, входит как рекламодатель, а при неизменном admin/admin — как администратор с управлением пользователями. Данные там вымышленные (тот же сид из репозитория), поэтому реальный ущерб — целостность и доступность стенда плюс риск переноса привычки `admin/admin` на боевой контур.

**Что сделать.** Заменить `passwordFor` на `randomUUID().slice(0, 16)` — ровно как уже сделано в `scripts/seed-campaigns.mjs:33` — и печатать пароль один раз в отчёте. Сгенерированное значение нужно протащить через `account`: тот же шаблон повторно вычисляется на `scripts/seed-stand.mjs:396`, когда скрипт логинится под брендом, иначе вход под существующей учёткой сломается. Убрать дефолты `admin/admin` из всех четырёх скриптов — читать из `SEED_LOGIN`/`SEED_PASSWORD` и падать с внятной ошибкой, если не задано. Убрать пару логин/пароль из README и сменить пароли всех уже заведённых учёток — правка скрипта задним числом ничего не чинит.

### 2. MoneyPopover: каждое событие scroll порождает новую цепочку requestAnimationFrame

**Где:** `src/components/campaigns/MoneyPopover.jsx:79-106`

**Проблема.** Функция `track` при каждом вызове планирует новый кадр (`frame = requestAnimationFrame(track)`), и она же подписана на `scroll` с `capture: true` и на `resize`. Каждое событие прокрутки вызывает `track` синхронно, тот перезаписывает переменную `frame` новым id, а ранее запланированный кадр никто не отменяет — он срабатывает и порождает собственную бесконечную цепочку. В cleanup отменяется ровно один id.

**Чем грозит.** Пара секунд прокрутки таблицы при открытом поповере оставляет десятки параллельных rAF-циклов, живущих до перезагрузки страницы, каждый с `getBoundingClientRect` на кадр. Хуже другого: осиротевшая цепочка держит живым не «мёртвый», а рабочий `onClose` — в обоих местах это инлайновая стрелка над стабильным сеттером `useState` (`src/pages/Campaigns.jsx:1117`, `src/pages/ContractOverview.jsx:636`). Как только её якорь уходит из вьюпорта или исчезает из DOM (смена месяца, фильтра, рефетч списка), цепочка вызывает `onClose()` каждый кадр, и заново открытый поповер денег закрывается мгновенно — до перезагрузки вкладки.

**Что сделать.** Разделить измерение и цикл; эталон лежит рядом — `src/components/campaigns/StatusPopover.jsx:108-119`.

```js
const measure = () => { if (!anchorEl.isConnected) return onClose(); /* …setAnchor… */ }
const loop = () => { measure(); frame = requestAnimationFrame(loop) }
frame = requestAnimationFrame(loop)
window.addEventListener('scroll', measure, true)
window.addEventListener('resize', measure)
```

### 3. Сохранение бренда с договорами неатомарно: повтор после сбоя создаёт дубли

**Где:** `src/features/advertisers/queries.ts:120-215`, `src/components/forms/AdvertiserForm.jsx:268, 299-305`

**Проблема.** `mutationFn` выполняет цепочку независимых запросов без транзакции: создание бренда, PATCH бренда, затем поштучно DELETE / POST / PATCH по каждому договору. Промежуточной фиксации нет — падение любого шага оставляет часть изменений применённой на сервере, а мутация отклоняется целиком. Инвалидация висит в `onSuccess`, `onError` у мутации нет вообще (`queries.ts:211-214`), а форма в `onError` только показывает тост и не трогает `source`.

**Чем грозит.** При создании нового бренда `advertiserId = id ?? (await advertisersApi.create(advertiser)).id`: если POST прошёл, а следующий шаг упал, `source` остаётся `null`, и повторное «Добавить» заводит второго рекламодателя с тем же названием. При правке существующего — у уже созданных договоров в форме по-прежнему локальный id из `uid('ctr')`, и повтор создаёт их заново. Гипотетически (семантика DELETE в спеке не описана) повторный DELETE по уже удалённому договору роняет цепочку в самом начале, и карточка становится несохраняемой до перезагрузки. Реальные триггеры — обрыв связи со стендом, 5xx, валидация дат, пакета или `fileId`; уникальность номера договора сервер пока не проверяет.

**Что сделать.** Минимум, который закрывает большую часть: перенести инвалидацию из `onSuccess` в `onSettled` (кэш должен обновиться и после провала — часть запросов уже применилась) и в `onError` формы перечитать карточку через `advertisersApi.get(advertiserId)`, пересобрав `form`/`source` из свежего ответа, чтобы у созданных договоров появились настоящие id. Полное решение — копить в `mutationFn` применённые операции с подменой локальных id на серверные и отдавать этот аккумулятор наружу вместе с ошибкой.

### 4. «Динамика за 14 дней» на экране кампании — сгенерированный ряд, выданный за статистику

**Где:** `src/pages/CampaignStats.jsx:105-113, 209-237`

**Проблема.** Карточка кампании берёт данные из API, рядом показывает настоящие показы/клики/конверсии, а график под заголовком «Динамика за 14 дней» целиком строит `seededSeries()` из `src/lib/id.js` — детерминированный псевдослучайный генератор, заведённый для моков. Подписи оси при этом реальные (`lastNDates(14)` — последние 14 календарных дней от сегодня, а не период кампании), тултип форматирует значения как деньги и числа. Отличить выдуманный ряд от настоящего в интерфейсе невозможно.

**Чем грозит.** Блок рендерится в ветке `else` от `hasMediaTables` (`:95, 158`), то есть показывается для всех статусов, кроме `active` — ровно на завершённых, оплаченных и архивных заявках, где его и будут читать как итоговый отчёт. Маршрут `/app/campaigns/$campaignId` не имеет проверок роли, так что это видит рекламодатель. Кампания, отработавшая в марте, открывается с «динамикой освоения бюджета» за последние две недели сентября; при сверке с реальными выходами расхождение необъяснимо.

**Что сделать.** Подменить ряд настоящими данными сейчас нечем: в `src/api/types.ts:222-247` у `Campaign` только агрегаты, эндпоинта тайм-серий нет. Убрать карточку целиком (строки 209-237) вместе с `seededSeries`, `SegmentTabs`, `METRICS` и `lastNDates`, либо — если график нужен для демо на master — явно подписать его как демонстрационный и скрыть для роли `advertiser`. После удаления `seededSeries` не используется нигде в `src/`.

### 5. 403 гасит сессию наравне с 401, и разлогин происходит молча

**Где:** `src/api/client.ts:174`, `src/api/errors.ts:26-28`, `src/main.jsx:21-24`

**Проблема.** `ApiError.isAuthError` возвращает true и для 401, и для 403, а `perform()` на любой такой ошибке зовёт `onUnauthorized()`, который стирает сессию и весь кэш react-query, после чего подписка на стор уводит на `/login` — без единого сообщения. 403 в RBAC-панели означает «этой роли сюда нельзя», а не «токен недействителен».

**Чем грозит.** Сегодня все источники 403 закрыты UI-гейтами (`useVisibleAdvertisers`, `canManageUsers` в `src/pages/Advertisers.jsx:39`, `requireRoles` в роутере), воспроизводимого сценария нет — это налог на каждый новый экран: первый же хук, дёрнувший закрытый для роли эндпоинт, выкинет пользователя на `/login` с потерей открытых форм, и диагностировать это будет нечем. Матрица прав де-факто размазана по условным `enabled` в хуках вместо одного места. Наблюдаемая часть проблемы — честное истечение refresh: пользователь оказывается на экране входа и не понимает, сохранились ли правки.

**Что сделать.** Сначала дешёвое и видимое: показывать сообщение перед редиректом в `src/main.jsx:21-33` («Сессия истекла, войдите заново»). Затем заменить условие на `status === 401` в `client.ts:174` и завести отдельный признак `isForbidden` для 403, чтобы экраны показывали «Нет доступа к разделу». `isAuthError` в `src/lib/queryClient.ts:11` (запрет retry) трогать не нужно — повторять 403 действительно бессмысленно; логаут при провале refresh на `client.ts:165` тоже легитимен. После этого `enabled: !isAdvertiser` в `useVisibleAdvertisers` становится оптимизацией, а не защитой от разлогина.

### 6. Нет ни одной границы ошибок, включая ту, что фреймворк даёт бесплатно

**Где:** `src/router.tsx:153`, `src/api/client.ts:133-137`

**Проблема.** В проекте нет ни `componentDidCatch`, ни `getDerivedStateFromError`, ни `errorComponent`. Роутер создан как `createRouter({ routeTree })` без `defaultErrorComponent`, и это решающее условие: в `@tanstack/react-router` маршрут без `errorComponent` вообще не оборачивается в CatchBoundary (`node_modules/@tanstack/react-router/dist/esm/Match.js:44`), исключение уходит в корень React. Провайдеры в `main.jsx` тоже ничего не ловят. Параллельно весь `src/api/types.ts` держится на `return (await response.json()) as T`, а `docs/backend.md` уже фиксирует три расхождения сервера с собственной схемой (пп. 3.10, 3.11, 3.13).

**Чем грозит.** Исключение в рендере — например `CONTRACT_STATUS[status].label` на `src/components/campaigns/ContractPreviewModal.jsx:201` при значении статуса вне энума — размонтирует всё дерево: белая страница без шапки и навигации, лечится только перезагрузкой, причина никуда не логируется. Для списочных ответов падение чаще случается ещё внутри `queryFn` (`src/lib/paginate.ts:20`) и корректно попадает в `isError`, так что белый экран — сценарий именно для данных, разыменовываемых при рендере.

**Что сделать.** Первым шагом — одна опция: `createRouter({ routeTree, defaultErrorComponent, defaultOnCatch })`, экран по образцу `src/pages/NotFound.jsx` с кнопкой «Обновить». Падение локализуется маршрутом, а не гасит весь `/app`. Дополнительно — классовый boundary вокруг `<RouterProvider>` для ошибок провайдеров. Позже, по желанию, — схемы (zod/valibot, ~5 КБ) только на корневые ответы, от которых зависит сессия и права (`LoginResponse`, `MeResponse`, `Paginated<Advertiser>`, `Paginated<Campaign>`), с выводом типов через `z.infer`, чтобы определение осталось одно. Остальные эндпоинты можно оставить на `as T`.

### 7. vercel.json не отдаёт ни одного заголовка

**Где:** `vercel.json:1-9`

**Проблема.** Весь конфиг деплоя — два rewrite. Нет `Content-Security-Policy`, `frame-ancestors`/`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`. Заодно нет `Cache-Control: immutable` для файлов в `dist/assets`, хотя они содержат хеш в имени и неизменяемы по построению.

**Чем грозит.** Для панели, которая держит JWT в localStorage (`src/stores/authStore.ts:6`), CSP — единственный барьер, мешающий утащить токен на чужой домен после инъекции скрипта. Без `frame-ancestors 'none'` страницу можно открыть в невидимом iframe и подсунуть админу клик по деструктивной кнопке; сценарий многошаговый и требует, чтобы залогиненный админ сам зашёл на страницу атакующего, — но фикс стоит десять строк. Плюс каждый повторный вход ревалидирует ~300 КБ ассетов вместо чтения из кэша.

**Что сделать.** Добавить блок `headers`:

```
/(.*)         Content-Security-Policy: default-src 'self'; script-src 'self';
              style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
              media-src 'self' blob:; connect-src 'self'; frame-ancestors 'none';
              base-uri 'self'; object-src 'none'
              X-Content-Type-Options: nosniff
              Referrer-Policy: strict-origin-when-cross-origin
/assets/(.*)  Cache-Control: public, max-age=31536000, immutable
```

`'unsafe-inline'` в `style-src` нужен Tailwind и framer-motion, `blob:` — из-за `URL.createObjectURL` в `src/features/files/queries.ts:53,85`, `connect-src 'self'` работает, потому что API проксируется через свой origin. Внешний `https:` в `img-src` не нужен: логотипы либо локальные (`src/lib/seed.js:121-124`), либо приходят как `/api/v1/files/…`. Порядок rewrites менять не надо — на Vercel они применяются после проверки файловой системы. HSTS Vercel отдаёт сам.

### 8. Сборка не запускает ни typecheck, ни lint; автоматических проверок нет вообще

**Где:** `package.json:8-14`

**Проблема.** `"build": "vite build"`, а Vite транспилирует TS через esbuild и типы не проверяет. `.github/` отсутствует, husky и lefthook отсутствуют, `vercel.json` не переопределяет `buildCommand` — значит Vercel на обоих проектах выполняет именно `npm run build`. `npm run typecheck` и `npm run lint` существуют, но не вызываются ничем, кроме рук разработчика.

**Чем грозит.** Любая ошибка типов или ESLint уровня error (например `react-hooks/rules-of-hooks`) уезжает в прод зелёным деплоем. Сейчас `tsc` проходит чисто и 0 ошибок линта, но это состояние ничем не удерживается, а миграция JS→TS идёт постоянно. В ESLint часть правил уже переведена в warning с пометкой «вернуть в error», и без CI этот долг никем не отслеживается.

**Что сделать.** Завести `.github/workflows/ci.yml` на `pull_request` и push в master/dev: `npm ci && npm run lint && npm run typecheck && npm run format:check`. Основную пользу здесь даёт именно `eslint .` — он покрывает и `.jsx`, тогда как `tsc` при `checkJs: false` видит 29 файлов из 94, то есть самые крупные экраны (`Campaigns.jsx`, `Dashboard.jsx`) остаются вне проверки. Перед первым прогоном выполнить `npm run format` или добавить `.claude/` в `.prettierignore` — иначе `format:check` упадёт на `.claude/launch.json`. `"build": "tsc --noEmit && vite build"` полезен как второй барьер, но закрывает только TS-срез, продавать его как защиту от рантайм-падений нельзя.

### 23. CPM и CPA на карточке кампании всегда показывают 0

**Где:** `src/lib/metrics.js:7, 9`; использование — `src/pages/CampaignStats.jsx:194, 263`

**Проблема.** `cpm` и `cpa` берут расход из `c.spent`, но денег у кампании больше нет — они на договоре (`src/api/types.ts:220` говорит это прямым текстом). `undefined / n * 1000` даёт NaN, а `formatMoney` через `Number(v) || 0` превращает NaN в аккуратный ноль — ошибка не видна ни в консоли, ни в интерфейсе. Соседняя «Средняя цена клика» на `:272` посчитана правильно — от `spent` договора, поэтому на одной карточке соседствуют верная CPC и нулевые CPM/CPA.

**Чем грозит.** Завершённая кампания с 2 млн показов и договором на 300 млн показывает «CPM 0». **Что сделать.** Передавать расход явным аргументом: `cpm(spent, campaign.impressions)` и `cpa(spent, campaign.conversions)` — переменная `spent` договора уже посчитана на строке 93. Заодно удалить `pacing` (`metrics.js:11`) и `aggregate` (`:27-45`): они читают те же несуществующие поля и не импортируются нигде, а `pacing` везде считают инлайном (`ContractPreviewModal.jsx:101`, `CampaignPreviewModal.jsx:370`).

### 26. Refresh-токен персистится в localStorage

**Где:** `src/stores/authStore.ts:6, 19-48`

**Проблема.** zustand `persist` без `partialize` пишет в localStorage всё состояние — и `tokens` (access + refresh), и профиль. Ключ `setanta.auth.v3` доступен любому JS на origin. Транспорт при этом уже держит токены в памяти (`src/api/token.ts`), то есть для работы приложения из хранилища нужен только refresh.

**Чем грозит.** Любой XSS — свой код, скомпрометированный npm-пакет, расширение браузера — одним `localStorage.getItem('setanta.auth.v3')` забирает долгоживущий refresh, а CSP, которая ограничила бы отправку украденного токена, отсутствует (п. 7). **Что сделать.** Два честных варианта. Либо запросить у бэкенда refresh в httpOnly + SameSite=Strict cookie — прокси `/api` уже делает запросы same-origin, cookie пройдёт без изменений во фронте (пункт в один ряд с уже накопленными в `docs/backend.md`). Либо осознанно зафиксировать текущий размен комментарием в `authStore.ts`. `partialize` модель угроз не меняет: крадут именно refresh.

**Где:** `src/lib/store.js:287-304`, `src/main.jsx:38`

**Проблема.** `let state = load()` — побочный эффект на верхнем уровне модуля; `load()` синхронно парсит снимок и безусловно переписывает ключ обратно (строка 297), даже когда база актуальна, а `normalizeDatabase` идемпотентен. **Где:** `src/api/client.ts:103-129`

**Проблема.** В репозитории нет ни одного `*.test.*`/`*.spec.*`, нет `vitest.config`/`jest.config`, нет тестовых зависимостей и скрипта `test`. Для UI-слоя это терпимо, но одно место действительно алгоритмическое и не проверяется ни типами, ни глазами: single-flight refresh, где корректность держится на договорённости «параллельные обновления недопустимы» и на проверке `getAccessToken() === sentWith`.

**Чем грозит.** Регрессия в `refreshing`/`sentWith` ломает единственность обновления: страница открывается с протухшим access, три запроса стартуют одновременно, сервер гасит refresh, пользователя выкидывает на логин. Ни `tsc`, ни eslint, ни клик по счастливому пути этого не покажут. Остальные кандидаты слабее, чем кажутся: деления в `src/lib/metrics.js:3-11` уже защищены от нуля, разреженные строки в `src/lib/xlsx.js:40-50` разбираются по адресу ячейки с заполнением дырок, `MAX_PAGES = 20` прокомментирован как намеренная страховка.

**Что сделать.** `npm i -D vitest happy-dom` (happy-dom нужен из-за `DOMParser` в `xlsx.js:6`), `"test": "vitest run"`, `test: { environment: 'happy-dom' }` в vite.config.js — и один файл `src/api/client.test.ts`: два параллельных 401 дают ровно один `POST /auth/refresh` и ровно один повтор, `fetch` мокается через `vi.stubGlobal`. Добавить шагом в CI из п. 8. Разворачивать тесты шире имеет смысл по мере роста доли TS, а не сейчас.

### 48. Версия Node не зафиксирована в репозитории

**Где:** `package.json:1-10`

**Проблема.** Нет ни `engines`, ни `packageManager`, ни `.nvmrc`, ни `.node-version`. Локально Node v22.21.1, npm 10.9.4, lockfileVersion 3 — всё согласовано, но ни один файл в репозитории об этом не сообщает.

**Чем грозит.** Версия Node для сборки живёт в настройках проекта Vercel — вне репозитория, невидимо из кода и из ревью. Новый разработчик или новая машина собирают на чём попало, и расхождение вскрывается только по симптомам.

**Что сделать.** Добавить в package.json `"engines": { "node": ">=22 <23" }` и `"packageManager": "npm@10"`, плюс `.nvmrc` с содержимым `22` — Vercel читает `engines`, а `actions/setup-node` в CI подхватит `.nvmrc` через `node-version-file`. Теги, CHANGELOG и версионирование для пред-1.0 внутренней панели в середине миграции — пожелание к процессу, а не дефект.

### 49. Два backend-документа описывают одни эндпоинты по-разному, и актуальный не закоммичен

**Где:** `docs/backend.md:285-286, 308`, `docs/backend-mock.md` (untracked)

**Проблема.** §4 в `backend.md` и новый `backend-mock.md` описывают те же мок-разделы разными контрактами. По «Обзору» расходится способ передачи периода и состав методов: `PUT /overview/2026-08` против `PUT /overview?period=2026-08` плюс `DELETE`. По отчёту договора расхождение принципиальное: `GET /reports/spot?contract=Д-2026/901&period=2026-08` против набора эндпоинтов, привязанных к числовому id (`GET /contracts/:id/report-tabs`). Единственная правка в diff `backend.md` — добавленная ссылка на новый документ; дублирующий §4 оставлен на месте.

**Чем грозит.** Бэкендер, которому дали ссылку на репозиторий, видит только `backend.md` — второй файл untracked и до него не доедет — и реализует один контракт, пока фронт пишется под другой. Интеграция отчётов ляжет целиком, и переделывать придётся серверную сторону.

**Что сделать.** Закоммитить `docs/backend-mock.md`: сейчас единственная актуальная спецификация отчётов существует на одной машине. Удалить §4 из `backend.md`, оставив там ссылку — разделение простое: `backend.md` про подключённое API и претензии к нему, `backend-mock.md` про неподключённое. В шапку `docs/backend-spec.md` добавить строку, что документ исторический: он описывает React 18, ссылается на удалённые `src/pages/Login.jsx` и `src/context/AuthContext.jsx` и на ключ `live-spots.v4`, которого в коде уже нет (там v5). Перенумеровать разделы `backend.md` после удалённого §2 — косметика, битых перекрёстных ссылок там нет.

## План работ

Порядок построен так, чтобы каждый следующий шаг опирался на предыдущий: сначала то, что эксплуатируется или уже врёт пользователю, потом барьеры, которые не дадут этому вернуться, и только потом рефакторинг.

**Один вечер — по часу на пункт**

1. **Пароли на стенде (п. 1).** Единственная находка, которая эксплуатируется прямо сейчас и не требует ни XSS, ни доступа к машине. Сменить пароли уже заведённых учёток, убрать шаблон и дефолты `admin/admin` из четырёх скриптов, убрать пару логин/пароль из README.
2. **`defaultErrorComponent` в роутере (п. 6).** Несколько строк в `src/router.tsx:153` превращают белый экран в экран с кнопкой «Обновить» и локализуют падение маршрутом. Делать до всего остального: дальше будет правиться код, и цена ошибки сразу упадёт.
3. **Цифры, которые видит клиент (пп. 4, 23).** Убрать выдуманный график и починить CPM/CPA — обе правки в `src/pages/CampaignStats.jsx`, обе про числа, на которые рекламодатель может сослаться в разговоре.
4. **rAF в MoneyPopover (п. 2).** Локальная правка по готовому эталону из `StatusPopover.jsx:108-119`; лечит и утечку, и мгновенно закрывающийся поповер.
5. **Заголовки в vercel.json (п. 7).** Десять строк конфига: CSP, `frame-ancestors`, `nosniff`, `Referrer-Policy` и `immutable` для ассетов.

**Первая неделя**

6. **CI и окружение (пп. 8, 48, 46).** Workflow с `lint + typecheck + format:check` на PR, `engines`/`.nvmrc`, блок для `scripts` в ESLint. Именно этот пункт удерживает всё, что будет сделано дальше, поэтому он раньше рефакторинга, а не после.
7. **Пакет доступности (пп. 19, 20, 18, 21).** Четыре файла — `index.css`, `Toast.jsx`, `Modal.jsx`, `Field.tsx`. Каждая правка в одном месте расходится по всему UI; начать с `aria-label`/`useId` в Modal и `role="status"` в Toast (десять минут), затем контраст в `@theme`, затем перевод `Field` на `<div>` + `htmlFor` — он попутно чинит обход `disabled` у FilePicker.
8. **Путь записи (пп. 3, 15, 16).** Весь блок «сбой при записи»: инвалидация в `onSettled` и перечитывание карточки в `onError`, `isPending` на кнопке договора, `catch` на скачивании файлов. Один заход, одна тема, легко тестировать вручную.

**Вторая неделя**

9. **Вес бандла (пп. 25, 27).** `lazyRouteComponent` на маршрутах плюс ленивый `store.js` и снятие лишней записи в localStorage. Замеренный эффект — 758 → 512 кБ; вендорный чанк отдельно, если останется время.
10. **`src/lib/period.js` и `useContractMoney` (п. 24), следом — статус «Нет отметки» (п. 13).** Именно в таком порядке: второй пункт лечится тем же вынесенным `statusAt`, и делать его до выноса значит написать третью копию логики.
11. **Разведение 401 и 403 плюс словари через `satisfies` (пп. 5, 22).** Профилактика перед следующими экранами: после неё новый хук не выкинет пользователя из сессии, а забытый статус станет ошибкой сборки, а не падением рендера.
12. **Фоном, по мере сил.** Документация (пп. 9, 49 — начать с коммита `backend-mock.md`), затем мок-специфика: скоупинг медиаплана (п. 11), кнопка «Открыть статистику» (п. 12), импорт и экспорт xlsx (пп. 14, 44), мёртвый код и форматтеры (пп. 36, 37, 41, 42). Раздел «Отчёт» (п. 10) решается одним продуктовым решением — снять маршрут или подписать как демо; отложить его дальше первой недели не стоит, потому что его видит внешний клиент.

## Что проверено и признано нормальным

- **Транспорт и сессия.** Единая точка `fetch`, single-flight refresh с проверкой смены access, корректные списки `ANONYMOUS_PATHS`/`NO_REFRESH_PATHS`, скачивание файлов через токен вместо прямых ссылок. Типовой гонки при параллельных 401 нет.
- **Границы слоёв.** Правило «в сеть ходим только из `src/api`» соблюдается: прямых обращений к `endpoints` из компонентов три, и все за чистыми утилитами (`isStoredUrl`, `absoluteUrl`, `isApiError`).
- **React-корректность.** Производные данные считаются на рендере вместо дублирования в состоянии, мутаций состояния нет, условных вызовов хуков нет, подписки на `document`/`window` почти везде снимаются, `key={index}` только в неперестраиваемых списках графиков. Большинство warning'ов eslint про `set-state-in-effect` — осознанный паттерн «сброс формы при открытии» с зависимостью по id.
- **Состояния UI в API-разделах.** Loader на `isPending`, EmptyState с текстом ошибки и кнопкой «Повторить» на `isError`, отдельный EmptyState на пустой список — закрыты во всех четырёх живых разделах. Формы не закрываются на ошибке и подхватывают `error.fields` в поля.
- **Типы.** `strict: true`, `noUnusedLocals`/`noUnusedParameters`, ноль `any`, `@ts-ignore` и `@ts-expect-error`, четыре каста на весь проект, `npx tsc --noEmit` проходит чисто.
- **Зависимости.** 25 прод-пакетов, лишних тяжёлых нет — `fflate` действительно нужен, потому что XML парсится самостоятельно, а zip-контейнер распаковывается через `unzipSync`/`zipSync`. Три уязвимости из `npm audit` — dev-only внутри цепочки ESLint, в браузер не попадают; `npm audit fix` проверенно безопасен и трогает только транзитивные версии.
- **Гигиена репозитория.** `dist` в `.gitignore` и отсутствует в индексе, `package-lock.json` закоммичен (lockfileVersion 3), `.env` исключён с сохранением `.env.example`.
