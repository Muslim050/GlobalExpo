# Разделы без API: что нужно от бэкенда

Аудит ветки `dev` по коду фронта: прошли по всем экранам и разделили их на
то, что уже ходит в API, и то, что до сих пор живёт на демо-данных.

По каждому неподключённому разделу здесь три вещи:

1. **эндпоинты**, которых не хватает;
2. **поля, которые фронт читает прямо сейчас** — это форма мока, и её нужно
   покрыть один в один, иначе экран не соберётся;
3. **чего в моке нет** — то, что к этим данным придётся добавить на сервере.

Соседние документы: [backend.md](backend.md) — состояние подключённых
эндпоинтов и претензии к ним; [backend-spec.md](backend-spec.md) — полная
спецификация модели данных.

| -------------------------- | ------------------------ | -------------------------------------------------- | ------------------------------- |

| Отчёт по договору          | вкладки внутри кампаний  | `/contracts/:id/reports/*` — семь листов из файла  | на API, кроме Total, Spot и OTT |

Мок-база лежит в `localStorage` под ключом `bloom.db.v12`, таблицы отчёта —
под собственными ключами `setanta.campaign.*`. То есть данные у каждого
человека свои и не переживают смену браузера.

## Общее: три решения, которые нужны до кода

**1. Отчёты ни к чему не привязаны.** Состав вкладок фронт хранит по договору,
а содержимое таблиц и сводок — глобально: медиаплан с ключом `spot1` один на
всю платформу. Открой два разных договора — увидишь одни и те же строки. Это
дефект мока, но он показывает, чего нет в модели: **каждая таблица и сводка
должна принадлежать паре «договор + канал»**.

> В [backend-spec.md](backend-spec.md) §2.6–2.7 строки привязаны к `campaignId` —
> это устарело. С тех пор отчёт переехал на договор: вкладки открываются под
> выбранным договором, а карточка кампании показывает отчёт её договора.
> Привязка — `contractId`.

**2. Месяц.** Заголовок над отчётом гласит «Статистика за август 2026», но
месяц в ключ данных не входит — все месяцы показывают одно и то же. Если
отчёт ведётся помесячно (а он ведётся: договор закрывается актом за месяц),
`period=YYYY-MM` нужен в адресе каждого отчётного эндпоинта.

**3. Правится руками, а не считается.** Все сводки отчёта — редактируемые
поля, а не агрегаты. Менеджер открывает панель, вбивает цифры из выгрузки и
сохраняет. Значит сводка — **хранимая сущность**, а не `SELECT SUM(...)`.
Даже там, где сумму можно посчитать (публикации соцсети), интерфейс не
считает: «Публикации» и «Impressions» ведутся отдельно от строк.

**Роли** во всех отчётных разделах одинаковые:

| Роль         | Что может                                                                         |
| ------------ | --------------------------------------------------------------------------------- |
| `admin`      | видит всё, правит всё                                                             |
| `viewer`     | только чтение; **не видит** просмотры (`views`, Live Ads Views), устройства и гео |
| `advertiser` | только чтение и только по своему бренду                                           |

Скрытие колонок у `viewer` сейчас делает фронт. Правильнее — не отдавать эти
поля в ответе вовсе.

## Общее: поля, которых нет ни в одной мок-сущности

Мок писался под localStorage, поэтому в нём нет ничего служебного. Ко **всем**
новым сущностям из этого документа нужно добавить:

| Поле                       | Зачем                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`                       | числовой, как во всём остальном API. В моке строковые и сгенерированные на клиенте: `sc_instagram`, `spot_ab12`, `ctr_artel_02`                        |
| `contractId` / `channelId` | привязка отчётных данных; в моке её нет вовсе                                                                                                          |
| `period`                   | `YYYY-MM` — месяц отчёта; в моке нет                                                                                                                   |
| `position`                 | порядок строк в таблицах и списках. Сейчас порядок = порядок массива, и он значим: логи идут по времени эфира, города — по убыванию доли               |
| `version`                  | оптимистичная блокировка — как у `Advertiser`, `Contract`, `Campaign`, `ManagedUser`. Отчёт правят несколько менеджеров, перетереть чужую правку легко |
| `updatedAt`, `updatedBy`   | «правил такой-то, тогда-то». Фронт это ещё не показывает, но для отчёта, который уходит клиенту, нужно                                                 |
| конверт списка             | `{ items, nextCursor, total }` — как у остальных списков, а не голый массив                                                                            |

И одно решение по типам. **В моке все значения сводок и таблиц — строки**:
поле ввода отдаёт строку, а фронт разделяет разряды прямо в нём (`14 111 352`).
На API числа лучше отдавать числами — фронт форматирует сам, он это уже умеет.
Исключение — хронометраж в медиаплане (`pre`, `mid1`, `mid2`, `post`): там в
файлах встречается и `30`, и `30 сек`, поэтому строка безопаснее.

## 1. Обзор

**Экран** `/app/overview` (`src/pages/Dashboard.jsx`).
**Доступ:** `admin` правит, `viewer` смотрит, `advertiser` не видит раздела.

Помесячный отчёт площадки: один документ на месяц, админ правит его прямо на
странице — каждое число на экране это поле ввода. Две вкладки: «Медиа и
аудитория» и «YouTube аналитика».

```
GET    /overview?period=2026-08       → OverviewReport   (admin, viewer)
PUT    /overview?period=2026-08       → OverviewReport   (admin) — документ целиком
DELETE /overview?period=2026-08       → 204              (admin) — вернуть значения по умолчанию
```

Фронт правит черновик и сохраняет по кнопке — `PUT` со всем документом
совпадает с текущим поведением и проще частичных патчей. `DELETE` — это
кнопка «Сбросить» на экране.

### Поля, которые читает фронт

Эталон — `src/lib/overviewSeed.js`, оттуда же удобно взять фикстуры.

| Путь                          | Тип                                                   | Что это                                                                               |
| ----------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `summary.title`               | string                                                | заголовок блока, правится текстом                                                     |
| `summary.subtitle`            | string                                                | подзаголовок, правится текстом                                                        |
| `summary.publications`        | number                                                | число публикаций                                                                      |
| `summary.socialImpressions`   | number                                                | охват в соцсетях                                                                      |
| `mediaTotals[]`               | `{ id, label, value, icon }`                          | прямые эфиры, ролики, промо, хронометраж (сек.), просмотры Live Ads. `label` правится |
| `socialChannels[]`            | `{ id, name, icon, color, posts, impressions, rows }` | Instagram и Telegram; строки добавляются и удаляются                                  |
| `socialChannels[].rows[]`     | `{ id, value }`                                       | охват одной публикации, рисуется столбиком                                            |
| `youtube.channel`             | string                                                | название канала                                                                       |
| `youtube.totals[]`            | `{ id, label, value }`                                | просмотры, лайки, дизлайки, комментарии, минуты просмотра                             |
| `youtube.breakdown[]`         | `{ id, title, items }`                                | четыре разбивки: пол, возраст, гео, девайсы                                           |
| `youtube.breakdown[].items[]` | `{ id, label, value }`                                | доля в процентах, дробная (`34.7`)                                                    |
| `audience.malePct`            | number (%)                                            | доля мужчин                                                                           |
| `audience.ageTitle`           | string                                                | заголовок блока возраста                                                              |
| `audience.ageNote`            | string                                                | примечание под ним                                                                    |
| `ageShare[]`                  | `{ id, label, value, color }`                         | доли возрастных групп, сумма 100                                                      |
| `deviceShare[]`               | `{ id, label, value, color }`                         | браузер, Smart TV, телефон, планшет                                                   |
| `platformDeviceShare[]`       | `{ id, platform, data }`                              | `platform` = `OTT` \| `TV`, `data` — такой же список долей                            |
| `leagueAgeRows[]`             | `{ id, sport, leagues, ages }`                        | `leagues` — строка через запятую, `ages` — **массив из 4 чисел**                      |
| `cityShare[]`                 | `{ id, name, value }`                                 | 22 города, доли в процентах                                                           |

Добавляются и удаляются на экране: `socialChannels`, их `rows`, `ageShare`,
`deviceShare`, группы `platformDeviceShare`, `leagueAgeRows`, `cityShare`.
Новая запись создаётся на клиенте с `id` вида `sc_x1y2` — на API `id` должен
приходить с сервера после сохранения.

`icon` — **ключ из закрытого списка**, не путь и не URL:
`RadioTower`, `Clapperboard`, `Tv`, `Timer`, `PlayCircle`, `Instagram`, `Send`.
`color` — hex-строка. Оба поля чисто оформительские; если не хотите держать их
в базе, скажите — фронт подставит по названию.

### Что добавить к этим данным

| Что                           | Зачем                                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `period`                      | сейчас месяц — это ключ в localStorage, в самом документе его нет                                                                                      |
| `updatedAt`, `updatedBy`      | показать «обновлено 12.09, Иванов» над отчётом                                                                                                         |
| `isDefault` (или `hasEdits`)  | документ за месяц ещё не заполняли — фронт покажет пустое состояние вместо демо-цифр                                                                   |
| `ages` → `[{ label, value }]` | сейчас это четыре числа, а подписи `18–24 / 25–34 / 35–44 / 45–54` **зашиты в разметку таблицы**. Если группы когда-нибудь поменяются, сломается молча |
| `position` у всех списков     | порядок городов и возрастных групп значим                                                                                                              |

### Вопросы

- Откуда берутся цифры: выгрузка из аналитики или ручной ввод? Интерфейс

- YouTube-разбивки приходят выгрузкой из YouTube Analytics. Тянуть их

## 2. Отчёт по договору

> **Состояние на 27.09.2026.** Бэкенд сделал отчёт за месяц
> ([reports-api.md](reports-api.md)): площадка загружает файл статистики,
> сервер разбирает его на семь листов, отдаёт, принимает правку и выгружает
> обратно в Excel. Фронт подключён целиком — эфиры, логи выходов, промо и
> соцсети теперь с сервера (2.2, 2.3, 2.5 закрыты), вкладки листов
> постоянные (2.1 закрыт для них).
>
> **На моке остались:** сводки Spot и Total (2.4) и категория OTT — в файле
> их нет. Эндпоинты на стенде `setanta.pythonanywhere.com` пока не
> выкачены: `GET /contracts/16/reports` отвечает `404`, в схеме их нет.
> Фронт проверен на ответах из описания.

Самый большой кусок. Вкладки живут в двух местах: на `/app/campaigns` под
выбранным договором и на карточке кампании `/app/campaigns/:id`. Собирает
отчёт `admin`, `viewer` и `advertiser` только читают.

Устроено так: постоянные вкладки `Total` и `Spot` — сводки, всё остальное
менеджер добавляет сам из **закрытого списка категорий**. Категория приносит
с собой два канала:

| Категория       | Каналы (`id`)             | Тип таблицы   |
| --------------- | ------------------------- | ------------- |
| `Live spot`     | `spot1`, `spot2`          | медиаплан     |
| `Standart spot` | `ss1uzb`, `ss2uzb`        | лог выходов   |
| `Event promo`   | `promo1`, `promo2`        | лог выходов   |
| `Social media`  | `social_ig`, `social_tg`  | отчёт соцсети |
| `OTT`           | `ott_live`, `ott_preroll` | лог выходов   |

Категории не придумываются руками — выбираются из этого списка
(`CATEGORY_PRESETS` в `src/components/campaigns/CampaignMediaTabs.jsx`).
Значит справочник категорий и каналов — серверный, а не пользовательский.

### 2.1 Состав вкладок

Сейчас: `localStorage`, ключ `setanta.campaign.custom-tabs.v2`, разложен по
договорам.

```
GET    /contracts/:id/report-tabs        → { categories: [...], channels: [...] }   (все роли)
POST   /contracts/:id/report-categories  { name }  → категория с её каналами        (admin)
DELETE /report-categories/:id            → 204                                       (admin)
```

**Что читает фронт:**

| Поле                    | Тип                         | Комментарий                                              |
| ----------------------- | --------------------------- | -------------------------------------------------------- |
| `categories[].id`       | string                      | в моке `cat_1`, `cat_2`                                  |
| `categories[].name`     | string                      | ровно как в справочнике: `Live spot`, `Standart spot`, … |
| `channels[].id`         | string                      | `spot1`, `ss1uzb`, `social_ig` — **ключ таблицы**        |
| `channels[].categoryId` | string                      | к какой категории относится                              |
| `channels[].label`      | string                      | подпись вкладки: `Setanta Sports 1`, `SS1`, `Instagram`  |
| `channels[].kind`       | `plan` \| `log` \| `social` | какую таблицу открыть                                    |

**Что добавить:** `position` категорий и каналов (порядок вкладок на ленте) и
серверный справочник пресетов — сейчас список категорий зашит во фронт, и
добавить категорию без релиза нельзя:

```
GET /report-category-presets → [{ name, kind, hint, channels: [{ id, label, kind }] }]
```

Удаление категории **не должно удалять таблицы**: интерфейс обещает, что
строки вернутся, если категорию добавить снова.

### 2.2 ~~Медиаплан Live spot~~ — закрыт листами `live1`, `live2`

Таблица размещений в прямых эфирах: `spot1`, `spot2`. Правится по ячейкам,
строки добавляются и удаляются, есть импорт `.xlsx` перетаскиванием и выгрузка
обратно. Сохранение — по кнопке, таблицей целиком.

Сейчас: `setanta.campaign.live-spots.v5`, значения по умолчанию —
`src/lib/liveSpotSeed.js`.

```
GET /contracts/:id/media-plan/:channel?period=2026-08   (все роли)
PUT /contracts/:id/media-plan/:channel?period=2026-08   { rows: [...] }   (admin)
```

**Что читает фронт** — все поля строками, как в таблице:

| Поле         | Тип    | Пример              | Комментарий                          |
| ------------ | ------ | ------------------- | ------------------------------------ |
| `id`         | string | `spot_ab12`         | в моке генерируется на клиенте       |
| `date`       | string | `Thu, Jan 1`        | **как в файле**, без разбора в дату  |
| `time`       | string | `21:30`             | подпись колонки — «Время GMT+4»      |
| `tournament` | string | `Premier League`    |                                      |
| `event`      | string | `Liverpool - Leeds` |                                      |
| `channel`    | string | `S1`                | при импорте подставляется по вкладке |
| `pre`        | string | `30`                | хронометраж, секунды                 |
| `mid1`       | string | `15`                |                                      |
| `mid2`       | string | `15`                |                                      |
| `post`       | string | `30`                |                                      |
| `views`      | string | `198214`            | **не отдавать роли `viewer`**        |

Под таблицей две строки итогов, их считает фронт — но на бэке удобнее отдавать
готовыми вместе со строками:

```json
{ "rows": [...],
  "totals": { "rows": 42, "spots": 168, "pre": 1260, "mid1": 630, "mid2": 630, "post": 1260,
              "seconds": 3780, "views": 8734291 } }
```

- «Итого: N спотов · N×4 вставок» — это `rows` и `rows × 4`;
- суммы по `pre`, `mid1`, `mid2`, `post`, `views`;
- «Итоговая сумма секунд» = `pre + mid1 + mid2 + post` за период.

**Что добавить:** `contractId`, `channelId`, `period`, `position`, `version`,
`updatedAt`/`updatedBy`. И решить по датам: хранить `date`/`time` строкой (как
сейчас, файл в файл) или разбирать в `datetime`. Строка проще и не ломает
импорт; `datetime` даёт сортировку и фильтр по дням — тогда фронту нужно
отдавать и исходную подпись, иначе `Thu, Jan 1` не восстановить.

### 2.3 ~~Логи выходов~~ — закрыты листами `ss1uzb`, `ss2uzb`, `promo1`, `promo2`

Построчная выгрузка из «Шаблона импортируемого отчёта Setanta Statistics»:
`ss1uzb`, `ss2uzb`, `promo1`, `promo2`, `ott_live`, `ott_preroll`. Основной
сценарий — импорт `.xlsx` (фронт сам разбирает книгу и приводит даты Excel к
`дд.мм.гггг`, время — к `чч:мм:сс`). Правка ячеек руками не предусмотрена:
только импорт, очистка и сохранение.

Сейчас: `setanta.campaign.spot-logs.v1`, демо — `src/lib/spotLogSeed.js`.

```
GET /contracts/:id/logs/:channel?period=2026-08   (все роли)
PUT /contracts/:id/logs/:channel?period=2026-08   { rows: [...] }   (admin)
```

**Что читает фронт** — три колонки, и всё:

| Поле   | Тип    | Пример                                  |
| ------ | ------ | --------------------------------------- |
| `item` | string | `CLIENT - 10 PER DAY - 30 Sec - UZB TV` |
| `date` | string | `01.01.2026`                            |
| `time` | string | `19:09:13`                              |

**Что добавить:** `id` — у импортированных строк его **нет вообще**, фронт
клеит ключ из `item + date + time + индекс`. Дальше `contractId`, `channelId`,
`period`, `position`, и по желанию `importId` / `importedAt` — чтобы было
видно, из какой загрузки строка и когда её залили.

**Объём.** Месяц выходов на четыре вкладки — порядка 2400 строк, за год по
всем договорам это десятки тысяч. `PUT` целиком для такой таблицы нормально
(один импорт = одна замена), а вот `GET` стоит сразу сделать страничным,
`limit` + `cursor`, как в остальных списках.

**Разбор файла.** Сейчас `.xlsx` разбирает браузер (`src/lib/xlsx.js`, свой
парсер на fflate — сторонних библиотек нет). Если разбор переедет на сервер,
эндпоинт `POST /contracts/:id/logs/:channel/import` с `multipart` закроет
вопрос и заодно снимет разброс форматов дат между браузерами. Скажите, что
удобнее — фронт подстроится.

### 2.4 Сводки Spot и Total

Две постоянные вкладки. Обе редактируются целиком: кнопка «Редактировать» →
поля → «Сохранить».

Сейчас: `setanta.campaign.report-stats.v1`, ключи `spot` и `total`.
Демо-значения — в `src/components/campaigns/CampaignReportPanels.jsx`.

```
GET /contracts/:id/report-stats/:panel?period=2026-08    panel = spot | total   (все роли)
PUT /contracts/:id/report-stats/:panel?period=2026-08                            (admin)
```

**Панель `spot`:**

| Поле                         | Тип    | Комментарий                             |
| ---------------------------- | ------ | --------------------------------------- |
| `channels[].code`            | string | `S1`, `S2` — им же рисуется плашка      |
| `channels[].name`            | string | правится текстом                        |
| `channels[].standardSpots`   | number | Standard spot, роликов                  |
| `channels[].standardSeconds` | number | Standard spot, секунд                   |
| `channels[].liveAds`         | number | Live spot UFC / Football, Live Ads      |
| `channels[].liveSeconds`     | number | Live spot UFC / Football, секунд        |
| `channels[].liveViews`       | number | TV Live Ads Views — **не для `viewer`** |
| `eventPromo`                 | number | TV Event Promo Count                    |
| `ottPreroll`                 | number | OTT Pre-roll Views                      |

**Панель `total`:**

| Поле        | Тип                            | Комментарий                                                                                                                                            |
| ----------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `metrics[]` | `{ label, value }`             | пять метрик: прямые эфиры, ролики, промо, хронометраж, просмотры Live Ads. **`label` — ключ**: по нему подбирается иконка и прячется строка у `viewer` |
| `social[]`  | `{ name, posts, impressions }` | `name` = `Instagram` \| `Telegram`, по нему берутся иконка и цвет                                                                                      |
| `devices[]` | `{ label, value, color }`      | доли устройств, рисуется бубликом. **Не для `viewer`**                                                                                                 |
| `cities[]`  | `{ name, value }`              | город и доля в процентах, строки добавляются и удаляются. **Не для `viewer`**                                                                          |

**Что добавить:** `contractId`, `period`, `version`, `updatedAt`/`updatedBy`,
`position` у `cities`. И заменить `label`/`name` как ключи на честные коды —
сейчас `metrics[].label` это одновременно подпись на экране и идентификатор
метрики: переименуешь подпись — потеряется иконка и перестанет работать
скрытие у `viewer`. Нужен `key` (`liveBroadcasts`, `ads`, `promo`, `seconds`,
`liveAdsViews`) плюс отдельный `label`. То же самое у `social[].name`.

Сохранённую панель фронт склеивает с эталоном: если в API появится новый блок,
старые записи не должны ронять экран — то же самое стоит сделать и на сервере
(отдавать недостающие поля значениями по умолчанию).

### 2.5 ~~Отчёты соцсетей~~ — закрыты листом `social`

Вкладки `social_ig` и `social_tg`: список публикаций со ссылками и показами,
плюс два числа над списком.

Сейчас: `setanta.campaign.social.v1`, ключ — id канала.

```
GET /report-channels/:id/social?period=2026-08    (все роли)
PUT /report-channels/:id/social?period=2026-08    (admin)
```

| Поле           | Тип    | Комментарий                                                |
| -------------- | ------ | ---------------------------------------------------------- |
| `posts`        | number | «Публикации» — ведётся руками                              |
| `impressions`  | number | «Impressions» — ведётся руками                             |
| `rows[].id`    | string | в моке `soc_x1y2`                                          |
| `rows[].link`  | string | без схемы: `instagram.com/XXXXXXX`, `t.me/setanta_uzb/123` |
| `rows[].views` | number | охват публикации                                           |

`posts` и `impressions` **не обязаны** совпадать с количеством и суммой строк —
считать их на сервере нельзя.

**Что добавить:** `contractId`, `channelId`, `period`, `position` строк,
`version`. И, если пойдёт разговор про отчёт по датам, — `publishedAt` у
публикации: сейчас у строки есть только ссылка и охват, когда вышел пост —
неизвестно.

## 3. Отчёт рекламодателя

**Экран** `/app/reports` (`src/pages/Reports.jsx`), доступен только роли
`advertiser`. Сейчас это та же панель `Total`, что и во вкладке отчёта, но по
смыслу — сводка по всем кампаниям бренда, а не по одному договору. Данные те
же демо-константы.

```
GET /reports/summary?from=2026-01-01&to=2026-12-31    (advertiser — по своему бренду)
```

Поля — как у панели `total` из 2.4, один в один: `metrics`, `social`,

| Поле           | Зачем                                                                               |
| -------------- | ----------------------------------------------------------------------------------- |
| `advertiserId` | чей отчёт — фронт покажет бренд в шапке                                             |
| `from`, `to`   | эхо периода: подпись «за январь — декабрь 2026»                                     |
| `contracts[]`  | по каким договорам собрана сводка (номер и срок) — иначе цифра висит без объяснения |

Период фронт пока не передаёт, но параметры стоит заложить сразу: иначе отчёт
за год и за месяц не различить.

## 4. Статистика кампании

**Экран** `/app/campaigns/:id` (`src/pages/CampaignStats.jsx`). Сама кампания
и деньги договора приходят из API — не подключены три вещи.

### 4.1 График за 14 дней

Переключатель «Расход / Показы / Клики», под ним область. Ряд генерируется на
клиенте из итогового числа функцией `seededSeries()` — то есть **нарисован, а
не измерен**. Одинаковый при каждой перезагрузке, поэтому выглядит достоверно,
но к реальности отношения не имеет.

```
GET /campaigns/:id/timeseries?metric=spent|impressions|clicks&days=14
→ { "metric": "impressions", "points": [{ "date": "2026-08-01", "value": 12043 }] }
```

Фронту достаточно `date` + `value`; `metric` в ответе — чтобы не перепутать
гонку запросов при быстром переключении. Если разреза по дням в системе нет —
скажите, уберём блок. Держать выдуманный график на экране, который показывают
рекламодателю, нельзя.

### 4.2 Площадки кампании

Блок «Площадки» читает `channelIds` кампании и тянет названия из мок-базы —
единственное место, где карточка кампании ещё смотрит в `localStorage`. Нужны
всего два поля: `name` и `color` (точка перед названием). Закроется вместе с
разделом «Площадки» (п. 5).

### 4.3 Метрики

`impressions`, `clicks`, `conversions` в схеме есть, но форма заявки их не
отправляет и сервер ничем не заполняет — у всех кампаний, заведённых через
интерфейс, там нули. Отсюда `CTR`, `CPM`, `CPA`, `CVR` на экране равны нулю.

Нужно решить: кто и когда проставляет эти числа — импорт отчёта, ручной ввод
площадкой или расчёт из логов выходов, — или убрать блок с экрана. Если
считать из логов, к кампании понадобится ещё и `spent` за период (деньги
сейчас лежат на договоре, а метрики — на кампании; `CPM` и `CPA` считаются по
обоим).

## 5. Площадки

**Экран** `/app/channels` (`src/pages/Channels.jsx`). Эндпоинты в схеме есть
(`GET/POST/PATCH/DELETE /channels`), но экран целиком работает на мок-базе:
создание, правка и удаление пишут в `localStorage`.

Раздел **скрыт из меню** (`hidden: true` в `src/lib/nav.js`) — по прямой ссылке
открывается, из навигации нет.

**Что читает фронт:**

| Поле       | Тип                                                       | Комментарий                                  |
| ---------- | --------------------------------------------------------- | -------------------------------------------- |
| `id`       | в моке строка `ch_prime`                                  | на API — число                               |
| `name`     | string                                                    | обязательное                                 |
| `type`     | `CTV` \| `TV` \| `Web` \| `Mobile` \| `Social` \| `Audio` | список в форме зашит                         |
| `format`   | string                                                    | `Pre-roll`, `Mid-roll`, `Native`, `Rewarded` |
| `reach`    | number                                                    | охват, больше нуля                           |
| `cpm`      | number                                                    |                                              |
| `fillRate` | number, 0–100                                             | заполняемость, рисуется прогрессом           |
| `status`   | `active` \| `inactive`                                    | в форме два значения: «Активен», «Отключён»  |
| `color`    | hex-строка                                                | из палитры в форме                           |

**Что добавить:** `version` (как у остальных сущностей), `createdAt` и
счётчик использования — в строке площадки стоит «CTV · 12 кампаний», и сейчас
фронт считает это сам, перебирая все кампании. На списке это лишняя выборка:
удобнее `campaignsCount` прямо в записи, как договаривались по брендам
([backend.md](backend.md), п. 3.17).

**Сначала нужно решение, нужен ли раздел в проде.** Если да — подключаем за
час, эндпоинты готовы. Если нет — удаляем экран, форму и `channelIds` из
кампании. Сейчас он висит между: и в схеме, и в моке, и в меню его нет.

## 7. Кто в сети

**Экран** `/app/advertisers`, вкладка «Кто в сети» (`src/pages/Presence.jsx`).
**Доступ:** только `admin` — вкладка стоит рядом с «Пользователями».

Просьба клиента: видеть, кто из людей работает в платформе прямо сейчас.
Какой раздел у человека открыт, клиенту не нужно — поля `section` нет.
Экран собран и показывает демо-раскладку из `src/lib/presenceSeed.js`:
карточки тех, кто в сети, и список «заходили раньше» по свежести захода.
Честен там только текущий пользователь — он действительно в платформе.

```
GET /presence → { online: [...], total: 13 }
```

**Что читает фронт:**

| Поле          | Тип              | Комментарий                                                        |
| ------------- | ---------------- | ------------------------------------------------------------------ |
| `userId`      | number           | связь с `GET /users`: имя, роль и бренд берутся оттуда             |
| `online`      | boolean          | человек в платформе прямо сейчас                                   |
| `lastSeenAt`  | datetime         | когда его видели в последний раз — по нему сортируется список ниже |
| `onlineSince` | datetime \| null | с какого момента он в сети; на карточке это «В сети 17 минут»      |

**Как это обычно делают.** Отдельного «присутствия» заводить не нужно:
достаточно обновлять `lastSeenAt` у пользователя на каждом авторизованном
запросе (middleware, раз в минуту на человека, чтобы не писать в базу на
каждый чих). Тогда `online` — это просто `lastSeenAt` свежее, чем N минут
назад; N стоит держать на сервере, чтобы клиенты считали одинаково.

**Что добавить:** `lastSeenAt` в `ManagedUser` пригодится и сам по себе —
в списке пользователей видно, кто давно не заходил.

## Порядок, который предлагаем

1. **Площадки** — решение «нужны / не нужны». Эндпоинты есть, стоит час.
2. **Обзор** — самый заметный раздел на моке и самый простой: один документ,
   один `GET`, один `PUT`.
3. **Сводки отчёта** (2.4, 2.5) — четыре эндпоинта, маленькие документы,
   закрывают половину вкладок.
4. **Состав вкладок** (2.1) — без него сводки некуда вешать на новом договоре.
5. **Логи и медиаплан** (2.2, 2.3) — самый большой кусок; до кода обсудить
   объём, пагинацию и место разбора `.xlsx`.
6. **Отчёт рекламодателя** (3) — переиспользует формат из п. 2.4.
7. **График кампании и метрики** (4) — либо данные, либо убираем блоки.
8. **Кто в сети** (7) — дешевле всего: `lastSeenAt` в `ManagedUser` закрывает
   почти всё, и экран под это уже собран.
9. **Уведомления** (6) — когда дойдут руки.

Первые три решают общую задачу: убрать `localStorage` из разделов, которые
показывают клиенту. Остальное — чтобы цифры на экране стали настоящими.
